Обучен экспериментальный CatBoost для времени от выгрузки контейнера до выезда из терминала: [веса, методика и результаты](../models/terminal-dwell/v1/README.md). После проверки масштаба массы обучение использует 21 129 июльских случаев, временная проверка — 14 542 сентябрьских. Это отдельная задача от готовности груза к исходящему парому; качество на Каспии не подтверждено.

`POST /api/v1/predictions/terminal-dwell` автоматически использует модель, если пакет загрузился. При отсутствии весов, optional ML-зависимостей, ошибке пакета/инференса либо неподдержанном входе отвечает алгоритм Monte Carlo с тем же форматом результата. `method`, `trained_on_history`, `model_loaded` и `fallback_reason` показывают фактическую ветку. `GET /api/v1/models/terminal-dwell` сообщает состояние загрузки.

Для ML: `uv sync --locked --group ml`, затем `uv run --group ml uvicorn app.main:app --port 8000`. Для fallback достаточно базовых зависимостей. `CASPIAN_DWELL_MODEL_DIR` выбирает пакет v1, `CASPIAN_DWELL_HISTORY_MODEL_DIR` — v2; пустое значение отключает соответствующий пакет. После смены весов нужен restart backend. Обучение v1: `uv run --group ml python -m scripts.train_terminal_dwell`; v2: `uv run --group ml python -m scripts.prepare_dwell_history`, затем `uv run --group ml python -m scripts.train_dwell_history`.

Пример запроса:

```json
{
  "observed_at": "2026-11-12T12:00:00+03:00",
  "container_size": 20,
  "container_type": "DRY",
  "gross_tonnes": 15,
  "mode": "auto",
  "fallback_duration": {
    "minimum_hours": 0,
    "typical_hours": 48,
    "maximum_hours": 168
  }
}
```

Ответ содержит P10/P50/P90 в `remaining_hours` и соответствующие UTC-даты в `release_at`. `mode=algorithm` явно выбирает fallback. Диапазон fallback — сценарное допущение, не обученная оценка. Вне области обучения включается fallback. Метод `predictTerminalDwell` добавлен в `api/public-data.client.ts`; frontend не менялся.

Проверка на открытых исторических данных: [отчёт за 30 дней](../data/validation/2026-11-12/report.md). Сопоставлено 5 760 почасовых прогнозов ветра на 24 часа с ERA5 в восьми портах. Это проверка погодного входа; точность грузового Monte Carlo пока не подтверждена: сопоставленных прогнозов/фактов груза в найденных источниках нет.

Повторить расчёт без сети: `uv run python -m scripts.validate_real_data --replay ../data/validation/2026-11-12` из `backend/`. Новая выгрузка без ключей: `uv run python -m scripts.validate_real_data --output ../data/validation/new-run --days 30`. Источники и SHA-256 сохранены в manifest; исходные HTML остаются локально в `backend/var/real-validation-raw/`, в Git — нормализованные факты и CSV.

Backend получает погоду Open-Meteo, дневную активность IMF PortWatch и опубликованные диспозиции Курык/ASCO без ключей. В каталоге 11 портов пяти стран; у восьми подтверждены координаты и PortWatch ID. Курык, Алят и Туркменбаши поддержаны endpoint диспозиций; отсутствие координат не мешает читать публикации операторов.

Сервис на 8000 также хранит отправки, документы и операции Casper в SQLite. Отдельный worker подписывает testnet deploy и проверяет результат по цепочке. Запись по умолчанию отключена. [Запуск, архитектура и API для фронтендера](../docs/TRANSIT_API.md). Старый mock на 4010 остаётся независимым инструментом разработки.

## Запуск

Python 3.12+ и uv. Из корня репозитория:

```bash
cd backend
uv sync --locked
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

- Swagger UI: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json
- Health: http://localhost:8000/api/v1/health

Настройки читаются из переменных окружения; `.env.example` — образец, сам по себе файл `.env` автоматически не загружается. Значения по умолчанию позволяют запустить сервис без конфигурации. Если нужен env-файл: `uv run --env-file .env uvicorn app.main:app --port 8000`.

## API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/v1/health` | Готовность локального сервиса; внешние источники при health не опрашиваются |
| `GET /api/v1/ports` | Каталог, координаты и доступность источников |
| `GET /api/v1/ports/{id}` | Один порт |
| `GET /api/v1/ports/{id}/weather?forecast_days=3` | Почасовой ветер, порывы, температура, осадки; от 1 до 7 календарных дней UTC |
| `GET /api/v1/ports/{id}/activity?days=30` | Судозаходы за последние 1–90 завершённых дней UTC |
| `GET /api/v1/sailings?port_id=kuryk` | Опубликованные суда и статусы; поддержаны `kuryk`, `alat`, `turkmenbashi` |

Пример:

```bash
curl 'http://localhost:8000/api/v1/ports/makhachkala/weather?forecast_days=1'
curl 'http://localhost:8000/api/v1/ports/aktau/activity?days=30'
```

Weather сохраняет `null`, исходные единицы и координаты модельной сетки. `issued_at=null`: время выпуска модели не выводится из времени HTTP-запроса. Ряды начинаются в начале календарного дня, поэтому UI выбирает нужный интервал по полному `time`, а не по индексу.

Activity возвращает фактические строки источника; отсутствующие дни перечислены в `missing_dates`, не заполняются нулями. `latest_available_date` — последний день с записью в запрошенном окне, не глобальная дата последней публикации. Нулевое значение источника сохраняется как ноль. Эти данные — оценка активности, не очередь, не загрузка причалов в процентах и не задержка груза.

`meta` содержит источник, атрибуцию, `fetched_at`, `source_updated_at`, качество и состояние кэша. Здесь `source_updated_at=null`, потому что используемые ответы не предоставляют надёжное время публикации. Не подменять его датой наблюдения.

`cache_status=live` означает успешный HTTP-запрос к источнику, а не live-наблюдение. Поэтому одновременно возможны `cache_status=live` и `stale=true`: например, в свежем ответе PortWatch последняя запись старше трёх дней. Порог три дня — эвристика отображения, не SLA поставщика.

При сбое источника отдаётся последний снимок с `cache_status=stale`; его дата сохраняется. Если старый activity snapshot относится к предыдущему календарному окну, ответ сохраняет старые `window_start/window_end` и содержит предупреждение `CACHED_WINDOW_DIFFERS_FROM_CURRENT_REQUEST`. UI должен показывать фактически возвращённый диапазон. Если снимка нет — 503 `SOURCE_UNAVAILABLE`, с `Retry-After`. Неподдержанный источник/неподтверждённые координаты — 422, неизвестный порт — 404.

## Стек и устройство

```text
Next.js → FastAPI routes → DataService → HTTPX → Open-Meteo / IMF PortWatch
                              ↕
                       SQLite snapshots
```

- `app/main.py` — HTTP-маршруты, lifecycle, CORS и единый формат ошибок.
- `app/models.py` — Pydantic DTO и валидация единиц/значений.
- `app/catalog.py` — чтение общего `data/ports.json`.
- `app/providers.py` — запросы и нормализация внешних JSON.
- `app/service.py` — свежесть, fallback, дедупликация и ограничение параллелизма.
- `app/cache.py` — последний корректный нормализованный и исходный ответ для каждого ключа.

Модульный монолит: один процесс uvicorn, SQLite для локального кэша. TTL погоды 30 минут, активности 6 часов; после ошибки cooldown 60 секунд. Одновременно не более четырёх upstream запросов, запросы одного ключа объединяются. На внешний запрос есть общий deadline и ограничение размера ответа 2 MB. Локальные ошибки БД не маскируются под успешный upstream ответ.

Кэш сохраняется в `backend/var/public-data.sqlite3`, исключён из Git: на ключ сохраняется один последний снимок. Locks/cooldown действуют в одном процессе; для нескольких replicas нужна общая координация. Перевозки, документы и очередь операций сохраняются отдельно в `backend/var/transit.sqlite3`. Worker использует Rust `casper-client`; ML и исходные документы в chain не переносятся.

## Подключение frontend

Использовать `api/public-data.client.ts` и `api/public-data.types.ts` из корня. Новый base URL — `http://localhost:8000/api/v1`, без Authorization. CORS по умолчанию разрешает localhost:3000 и 127.0.0.1:3000.

Не заменять пока `NEXT_PUBLIC_API_BASE_URL` для отправок: этот URL остаётся на 4010. Для нового клиента удобно добавить `NEXT_PUBLIC_DATA_API_BASE_URL=http://localhost:8000/api/v1`. Это имя для интеграции; текущий frontend его ещё не читает.

```ts
const dataApi = createPublicDataClient('http://localhost:8000/api/v1');
const ports = await dataApi.ports();
const weather = await dataApi.weather('makhachkala', 3);
const activity = await dataApi.activity('makhachkala', 30);
const sailings = await dataApi.sailings('kuryk');
```

На карте отображать только ports с координатами; отображать недоступность источников отдельно. График погоды заменить данными API, явно указав порт, даты и единицы. PortWatch показывать отдельным графиком дневной активности; не конвертировать counts в проценты загрузки или часы задержки.

## Диспозиции Курык и ASCO

`app/sailings.py` загружает только два фиксированных публичных URL: [Курык](https://portkuryk.kz/ru/dispoziciya-sudov) и [ASCO](https://cabinet.asco.az/passenger-ticket). BeautifulSoup разбирает проверенные заголовки и строки; страницы входа, неверные даты и изменившиеся таблицы отвергаются. Размер HTML ограничен 2 MB. Кэш — 15 минут (`CASPIAN_SAILINGS_TTL_SECONDS`), общий deadline и cooldown действуют как у остальных источников. Исходный HTML и нормализованный снимок сохраняются вместе.

Курык отдаёт записи `berth`, `anchorage`, `expected`; ASCO — `underway` и `in_port`. В каждой записи сохраняются имя судна, исходные порты, статус, время, причал при наличии и `weather_related`. Число автомашин в примечании не считается свободной вместимостью. Групповые названия судов сохраняются как одна опубликованная строка. `id` — идентификатор строки, не IMO/MMSI. Одинаковые имена из разных источников не объединяются автоматически.

Курык выдаёт свои записи только для `kuryk`; ASCO фильтруется по порту отправления/назначения. Баку не подменяет Алят. Неизвестные названия портов сохраняются и отмечаются предупреждением. Для другого известного порта — 422 `SOURCE_NOT_COVERED`, неизвестного ID — 404.

Время на страницах не содержит проверенного timezone: `timezone=null`, `source_updated_at=null`, `*_at_local` — локальные ISO-строки **без offset**. Не переводить их в UTC через браузерный `new Date()`. Показывать как «время источника, часовой пояс не подтверждён». `reported_date` и `reported_at_local` относятся к публикации; `fetched_at` — фактическое время получения в UTC. Курык публикует только дату сводки, ASCO — дату и время.

В строках Курыка отсутствует год: он восстанавливается относительно даты публикации, с обработкой перехода декабрь/январь; `year_inferred=true`, исходная строка сохранена. Это предположение парсера. Свежесть публикации оценивается по её дате: старше одного дня — `stale=true`, независимо от успешной загрузки.

`sources` содержит метаданные каждого доступного источника. Если источник отказал, но кэш есть — отдаётся stale snapshot. Если кэша нет — он попадает в `errors`, ответ содержит `partial=true` и данные оставшегося источника. Если недоступны все требуемые источники — 503. `partial=false` не гарантирует свежесть: проверять `sources[].stale`. Распознанные пустые таблицы ASCO возвращают пустой список с предупреждением; непроверенное пустое состояние Курыка отвергается, чтобы изменение DOM не выглядело отсутствием судов.

Тестовый набор расширен до 42 тестов: парсинг, локальное время, смена года, фильтрация портов, неверная структура, частичный отказ и сохранение последнего снимка. Новый клиент включает `sailings(portId)`.

## Модель готовности к погрузке

`POST /api/v1/predictions/readiness` — вычисляемый Monte Carlo baseline. `app/prediction.py` принимает от одного до двадцати маршрутов, распределения длительности этапов (minimum/typical/maximum в часах), окна отправлений и время начала с timezone. Используется треугольное распределение, от 100 до 10000 симуляций и фиксируемый seed. Дополнительных ML-зависимостей нет.

```text
ready = start + max(land_travel + terminal_processing, documents_ready)
              + weather_hold + loading_buffer
```

Для каждой симуляции выбирается первое отправление, у которого cutoff не раньше ready и явно подтверждена вместимость сценария. Возвращаются P10/P50/P90 готовности, вероятность пропуска cutoff первого рейса, вероятность отсутствия подтверждённого отправления в горизонте и условный ETA доставки. Если ни один sample не получил отправление, delivery_eta=null. Доля samples с доставкой видна отдельно; условные квантили нельзя показывать как безусловную гарантию.

Результат явно помечен `trained_on_history=false` и `input_quality=user_supplied_scenario`. Параметры не обучены на истории перевозок. Низкоуровневый endpoint принимает готовый сценарий. Новый `/shipments/{id}/recalculate` собирает реальную погоду и историю активности, затем преобразует их в длительности по открыто описанным сценарным правилам; фактическое расписание и вместимость оператора по-прежнему отсутствуют. Длительности независимы; корреляции и пороги работы судов требуют данных операторов. Sampling standard error описывает только шум Monte Carlo, не реальную точность прогноза.

```bash
curl -X POST 'http://localhost:8000/api/v1/predictions/readiness' \
  -H 'Content-Type: application/json' \
  --data-binary @../data/scenarios/readiness-normal.json
```

Команда выполняется из `backend/`. Второй вход — `readiness-weather-hold.json`; он демонстрирует, как небольшой сдвиг готовности приводит к ожиданию следующего рейса. TypeScript-клиент: `predictReadiness(body)`. Начальные примеры и формат будущих меток — [данные модели](../data/scenarios/README.md).

Тесты модели включают границу cutoff, параллельную подготовку документов, сутки ожидания следующего отправления, неизвестную вместимость, повторяемость и валидацию сценария. Дополнительно проверяются постоянное хранение и очередь Casper. Следующие модули: сбор/калибровка на реальной истории и волны по морским точкам.


## Сквозной расчёт карточки

`POST /api/v1/shipments/{id}/recalculate` сохраняет прогноз, четыре варианта к одному
назначению и ESG из одного расчёта. Требуются роль логиста, `expected_revision`,
`Idempotency-Key`. Допущения и источники приходят в `Shipment.planning`. Запись
прогноза не меняет паспорт; выбор маршрута и замена файла запускают worker.
Описание полей: [TRANSIT_API.md](../docs/TRANSIT_API.md); формулы и ограничения:
[ARCHITECTURE.md](../docs/ARCHITECTURE.md).
