# Данные для модели готовности

`readiness-normal.json` и `readiness-weather-hold.json` — синтетические воспроизводимые входы, не история перевозок. Оба сценария используют один маршрут и заданные окна погрузки. Во втором увеличено время погодного ожидания. Дата фиксирована для воспроизводимости; это не актуальное расписание.

Все длительности в часах, абсолютные даты с timezone. `documents_ready` — время от начала сценария до готовности документов; оно идёт параллельно транспортировке. `terminal_processing` включает очередь и обработку после прибытия. `weather_hold` — дополнительная задержка готовности, заданная пользователем. Она не вычисляется автоматически из высоты волн или скорости ветра.

`capacity_confirmed=true` в примерах — допущение сценария. Таблицы ASCO/Курыка не подтверждают свободное место конкретного груза, поэтому их строки нельзя автоматически преобразовывать в доступные для бронирования отправления.

Для будущей калибровки нужен [шаблон событий](../templates/transport-events.csv). Типы событий: `origin_departure`, `terminal_arrival`, `queue_enter`, `queue_exit`, `documents_ready`, `loading_ready`, `vessel_departure`, `destination_arrival`. `planned_at` и `actual_at` разделены; `recorded_at` фиксирует момент появления сведений в системе. Все времена UTC. Неизвестные значения оставлять пустыми. Обезличенный shipment_id должен связывать события одной перевозки.

Реальные ответы внешних источников сейчас сохраняются в SQLite-кэше backend (исходные и нормализованные). Это последние снимки, не обучающая выборка. Для неё нужен датированный архив наблюдений и событий перевозок; сбор/очистка такого датасета — следующий этап. Разделять обучение и проверку по времени, учитывая `recorded_at` и момент выпуска погодного прогноза. PortWatch counts не являются метками задержек.
