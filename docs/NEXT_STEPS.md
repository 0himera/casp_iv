# Следующий этап после интеграции frontend

Проверен frontend из `origin/main`, commit `8eede97` (PR #1, ветка frontend). Выполнены fetch и fast-forward локального main. Пользователь выбрал только источники без ключей: Open-Meteo, IMF PortWatch, открытые страницы Курык и ASCO. AISStream и любые сервисы с регистрацией/ключом исключены из текущего этапа.

Проверки: `bun install --frozen-lockfile`, `bun run lint` и `bun run build` завершились успешно, включая TypeScript. Поведение cache при online transition воспроизведено отдельно на установленном `@tanstack/query-core`. Браузерный end-to-end прогон в этой проверке не выполнялся.

## Что уже сделано

Frontend на Next.js содержит карту MapLibre, список грузов, схему этапов, сравнение маршрутов, паспорт, замену файлов, подтверждения ролей, журнал и polling операций. REST-клиент подключён к mock на 4010. Сценарии и мутации используют переданные backend версии и idempotency keys. Это позволяет сохранить существующий интерфейс при замене источников данных.

Пока отсутствуют настоящий сервис данных, вычисляемая модель задержек и контракт Odra. Карта использует пять статических портов, а погодный график — включённые в сборку JSON-снимки. Присутствие файла с ответом API не означает работающий live adapter.

## Наш следующий вертикальный срез

Обновление реализации: все четыре endpoint из таблицы ниже реализованы в `backend/` (порт 8000), включая кэш и ошибки. Диспозиции поддерживают Курык, Алят и Туркменбаши. Контракт: `api/public-data.openapi.json`; клиент: `api/public-data.client.ts`. Frontend пока нужно подключить к этому отдельному клиенту, сохранив mock URL для отправок.

Сначала дать интерфейсу реальные данные по одному выбранному порту, затем распространить тот же adapter на все поддержанные порты. На карте должны присутствовать Россия/Дагестан, Иран, Казахстан, Азербайджан и Туркменистан; наличие узла не означает наличие рейса между любой парой портов.

Расширение API первого среза:

| Endpoint | Ответ и источник |
| --- | --- |
| `GET /api/v1/ports` | Каталог портов и покрытие. Основа: `data/ports.json`. Узлы с null coordinates не ставятся на карту до проверки координат. |
| `GET /api/v1/ports/{id}/weather` | Ветер/порывы/осадки из Open-Meteo; координаты запроса и модельной сетки, единицы, почасовые UTC timestamps. Волны отдельным рядом с морской точкой. |
| `GET /api/v1/ports/{id}/activity?days=30` | Дневные судозаходы из PortWatch. Название метрики «Активность порта», не «Загрузка %». |
| `GET /api/v1/sailings?port_id=kuryk` | Опубликованные диспозиции Курык/ASCO: судно, источник, заявленные места/времена/статусы. Не подтверждённая бронь и не универсальное регулярное расписание. |

У каждого ответа: `source_url`, `fetched_at`, `source_updated_at` (nullable), `quality`, `stale`, `units`. У прогноза отдельно `valid_at` и доступный `issued_at`; unknown не заменять нулём. PortWatch date — дата агрегата, не дата публикации. Формат закрепить в OpenAPI и DTO до подключения UI.

Backend кэширует запросы, ограничивает timeout и сохраняет последний успешный снимок. При отказе показывает stale snapshot с возрастом, при отсутствии снимка — missing. Начальные интервалы кэша: погода 30 минут, PortWatch 6 часов, HTML операторов 15 минут. Это проектные настройки, уточняемые по условиям источников.

Сохранять исходные ответы и нормализованные данные отдельно. Для HTML проверять дату внутри публикации, часовой пояс и отсутствие полей; не считать сегодняшнюю загрузку страницы подтверждением свежести её содержимого. Не выводить неизвестные события из пустой таблицы.

## Порядок реализации

1. **Public data backend:** каталог + Open-Meteo + PortWatch, кэш и свежесть; один порт end-to-end, затем остальные. Frontend одновременно исправляет P0 выше.
2. **Оперативные данные:** parser Курык/ASCO; проверка времён и неоднозначных названий судов. Отдельно проверить координаты Курыка, Алята и Оли.
3. **Модель задержек:** расписания/окна обработки и Monte Carlo. PortWatch даёт контекст активности, но не метки задержек груза. Для обучения нужны фактические этапы перевозок; до их появления результат модели честно обозначается как симуляционный.
4. **Odra:** локально протестировать версии, роли, отзыв/expiry; развернуть TransitPassport в Casper testnet и подключить существующий Operation flow. Погоду/графики не писать в chain на каждом обновлении.
5. **Общий прогон:** выбранный порт → реальные данные с датами → сценарный риск → вариант маршрута → новая версия паспорта → testnet согласования. Недоступность источника не ломает экран и не превращается в «всё хорошо».

Не нужно ждать полного production backend для подключения frontend. Достаточно первого проверенного среза данных с устойчивым API. Текущий mock остаётся отдельным воспроизводимым режимом.
