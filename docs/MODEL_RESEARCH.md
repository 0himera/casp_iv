# Какие модели подходят для прогноза времени обработки контейнера

Реализован простой первый этап: [CatBoost v2 с историей и калибровкой](../models/terminal-dwell/v2/README.md).
MAE на прежнем периоде — 32,10 часа; LSTM/Transformer и прогноз после каждой стадии
не добавлялись. Разделы ниже сохраняют исходный исследовательский план и ограничения.

Исследование от 12.11.2026. Рекомендация: сначала проверить историю операций в CatBoost,
затем сравнить с небольшой LSTM. Transformer — следующий кандидат, если последовательность
даёт воспроизводимый выигрыш. Смена архитектуры сама по себе пока не обоснована.

## Что именно прогнозируем

В литературе задача называется **remaining time prediction / predictive process monitoring**:
по уже произошедшим событиям оценить время до завершения процесса.
Ближайшие аналоги — обработка контейнера в терминале и исполнение складского заказа.
Прогноз прибытия судна по AIS решает другую задачу и требует траекторий судов.

Наш v1 прогнозирует время от конца DISCHARGE до конца TRUCK_OUT. Он получает только
размер, тип, массу, час и день недели. Истории операций и текущей стадии у него нет.
На 14 542 сентябрьских случаях CatBoost даёт MAE 48,62 часа, RF с log-целью — 47,47,
действующий Monte Carlo fallback — 47,75. Преимущество CatBoost над fallback не установлено.
Покрытие интервала P10–P90: 68,6% у CatBoost и 47,4% у fallback вместо номинальных 80%.
Это результаты уже использованного теста, а не независимая проверка нового решения.
[Карточка v1](../models/terminal-dwell/v1/README.md),
[сравнение с fallback](../models/terminal-dwell/v1/fallback-comparison.json).

## Самые близкие опубликованные работы

### 1. Transformer на том же контейнерном журнале

**Enhancing Remaining Time Prediction in Business Process Monitoring via Cross-Entropy
Supervised Entity Embeddings and Transformer Model**, Mubake et al., 2025.
[Статья и DOI](https://wseas.com/journals/articles.php?id=11437),
[полный текст](https://wseas.com/journals/bae/2025/e425107-059%282025%29.pdf).

Использован тот же Mendeley Dwelling Time Dataset. Авторы строят последовательности
из 1–10 событий, кодируют категориальные признаки через embeddings и совместно обучают
прогноз оставшегося времени и следующего действия. Опубликованный MAE — 1414,49 минуты,
то есть около 23,57 часа.

Это **не доказательство двукратного улучшения относительно нашего v1**: прогнозы делаются
на разных стадиях процесса, целевые значения ограничиваются процентилями 0,1/99,9,
используется увеличение выборки добавлением шума к целевым значениям. В прочитанном
описании эксперимента не найден достаточно подробный протокол разделения по случаям
и времени; открытая реализация не найдена. Это ограничение воспроизводимости,
а не утверждение о фактической утечке в работе.

Что взять: историю событий, embeddings категорий и вспомогательную задачу next activity.
Сначала проверить пользу самой истории; сложную совместную функцию потерь пока отложить.

### 2. Складская логистика: бустинг близок к нейросетям

**Remaining Time Prediction in Outbound Warehouse Processes: A Case Study**, Penther et al., 2025.
[Статья](https://arxiv.org/abs/2509.18986),
[код авторов](https://github.com/ultrawaffle/ppm_remaining_time),
[данные](https://figshare.com/articles/dataset/Warehouse_outbound_event_log/29500898).

Это реальный журнал исходящих складских операций в авиационной логистике.
После очистки и выбора периода в эксперименте 41 927 случаев и 330 709 событий.
Признаки включают время с начала процесса, время с прошлого события и текущую нагрузку.

| Метод | MAE, минуты | Время обучения у авторов |
| --- | ---: | ---: |
| XGBoost | 613 | около 2 минут |
| DA-LSTM | 568 | 1,26 часа |
| SuTraN | 554 | 4,65 часа |
| PGTNet | 1390 | 0,8 часа |

Числа относятся к их задаче и оборудованию Apple M1 Pro, не к нашему терминалу.
Усложнение здесь даёт умеренный выигрыш; графовая модель оказалась хуже.
Код — MIT, данные — CC BY 4.0, скачивание публичное без API-ключа.
Проверены метаданные Figshare: минимальный опубликованный CSV — 73 123 087 байт,
`outbound_2024_06_10_obfuscated.csv`. Сам CSV в рамках этого исследования не скачан.
README репозитория предупреждает о настройках PyTorch под Apple Silicon:
код потребует адаптации окружения, готовые веса для нашего терминала не предоставлены.

Что взять: подготовку признаков из известных событий и сравнение моделей на одном наборе.
Складской набор полезен как внешний тест реализации метода, а не как валидация Каспия.

### 3. Большой сравнительный эксперимент

**Assessing the Performance of Remaining Time Prediction Methods for Business Processes**,
Roider et al., IEEE Access, 2024.
[Статья](https://ieeexplore.ieee.org/abstract/document/10679137/),
[авторский полный текст](https://open.fau.de/server/api/core/bitstreams/00920136-8579-4854-b3bc-20b2677722e1/content),
[код](https://github.com/RoiderJ/assessing_remaining_time_methods).

На 16 журналах авторы сравнили четыре простых baseline и XGBoost, DA-LSTM, PGT-Net.
В этом исследовании не обнаружили статистически значимого общего различия между
тремя обучаемыми методами. Отдельно разобрано, как изменение распределения длительностей
искажает интерпретацию MAE. Это аргумент за сильные baseline и проверку по стадиям,
а не универсальное утверждение о равенстве любых моделей.

Их нормировка nMAE использует медиану тестовых целей как диагностический ориентир.
Такую медиану нельзя выдавать за доступный в эксплуатации baseline.
У GitHub API лицензия этого репозитория не указана; открытый просмотр кода
не означает автоматически разрешение на его перенос.

### 4. Разделение данных и смещение завершённых случаев

**Creating Unbiased Public Benchmark Datasets with Data Leakage Prevention for Predictive
Process Monitoring**, Weytjens, De Weerdt, 2021.
[Статья](https://arxiv.org/abs/2107.01905),
[актуальный репозиторий авторов](https://github.com/hansweytjens/predictive-process-monitoring-benchmarks).

Авторы показывают две разные проблемы: пересечение истории и будущих результатов между
частями выборки и смещение у границы выгрузки, содержащей только завершённые случаи.
Если наблюдение заканчивается в сентябре, длинные сентябрьские случаи могут отсутствовать,
потому что завершились позже. Строгого train/test-разделения недостаточно, чтобы вернуть
отсутствующие записи. Лицензия репозитория в GitHub API не указана; используем методику.

В наших 95 587 подготовленных случаях все TRUCK_OUT относятся к июлю–сентябрю 2021 года.
После фильтра массы месячная медиана длительности падает с 78,64 часа для июльских
DISCHARGE до 36,99 для сентябрьских. Эти месячные когорты отличаются от train/validation/test
v1 и не являются дополнительными метриками модели. Падение совместимо и с изменением
процесса, и со смещением отбора; утверждать улучшение работы терминала по нему нельзя.
Числа и hash исходной подготовленной таблицы: [evidence.json](../data/research/remaining-time/evidence.json).

### 5. Готовая архитектура для сравнения последовательностей

**SuTraN: an Encoder-Decoder Transformer for Full-Context-Aware Suffix Prediction of
Business Processes**, ICPM 2024.
[Официальная реализация](https://github.com/BrechtWts/SuffixTransformerNetwork), MIT.

Есть SuTraN и LSTM baseline, обработка префиксов и разделение по времени.
Проверен код `Preprocessing/create_benchmarks.py`: предусмотрен строгий вариант разделения
с учётом завершения обучающих случаев. Веса на банковских BPI-журналах не являются
готовой портовой моделью. Архитектура подходит для второго этапа исследования,
когда более дешёвый эксперимент подтвердит ценность последовательности.

## Конкретный следующий эксперимент

1. **Зафиксировать два разных момента прогноза.** Track A: ровно конец DISCHARGE,
   как в v1. Track B: обновление прогноза после каждого известного события, начиная
   с DISCHARGE и до TRUCK_OUT. Завершённый TRUCK_OUT с нулевым остатком в оценку не включать.
   Результаты A и B публиковать отдельно: добавление поздних событий меняет сложность задачи.
2. **Собрать историю без будущего.** Для каждого `as_of` использовать только события
   с `End Timestamp <= as_of`: последнее действие, число и порядок выполненных действий,
   время с DISCHARGE, время с предыдущего действия, известные статусы документов,
   тип/размер/допустимая масса. Для Track A полезны интервалы между уже известными
   BAPLIE, VESSEL_ATB и DISCHARGE; будущие JOB_DEL/CUSTOMS_DEL использовать нельзя.
   `recorded_at` отсутствует, поэтому конец события остаётся приближением доступности.
   Случаи и категории с неоднозначными единицами массы обрабатывать явно.
3. **Разделить случаи до генерации префиксов.** Все префиксы одного случая должны быть
   в одной части; обучающие исходы должны быть известны к соответствующей исторической
   дате. Кодировщики, нормализацию и подбор параметров строить без теста. Оставить окно
   наблюдения исходов и отдельно проверить чувствительность к удалению конца выгрузки.
   На этом коротком наборе честная проверка после большого защитного окна может оказаться
   слишком маленькой — это результат аудита данных, а не повод уменьшать окно ради MAE.
4. **Проверить простые baseline.** Глобальная медиана, условные медианы/квантили по стадии
   и времени ожидания, затем типу/размеру, со сглаживанием и возвратом к общей группе.
   Для ожидающего контейнера условный остаток должен учитывать, что он ещё не выехал;
   простое вычитание elapsed из общей медианы недостаточно. Сравнить с действующим MC
   на тех же моментах прогноза; его результат v1 нельзя переносить на Track B.
5. **Обучить CatBoost с историей и небольшую LSTM.** Сначала бустинг на новых признаках;
   затем одна последовательная модель, например DA-LSTM, с теми же доступными событиями.
   Начальная компактная конфигурация для эксперимента: embeddings действий, один слой
   LSTM на 64 состояния, головы оставшегося времени/квантилей, early stopping.
   Это предложение, не результат подбора. XGBoost L1 — дополнительный табличный baseline.
   SuTraN запускать только если первые результаты оправдают затраты.
6. **Проверять и точку, и интервал.** MAE в часах, pinball loss, покрытие и ширина P10–P90;
   отдельно по стадии, возрасту случая и календарному периоду. Для Track B показывать
   среднее с равным весом каждого случая, чтобы длинные последовательности не доминировали.
   Интервалы калибровать на отдельном периоде и по целым случаям; оценивать на следующем.
   [Conformalized Quantile Regression](https://arxiv.org/abs/1905.03222) — кандидат,
   но временной дрейф и связанные префиксы не дают автоматически стандартную гарантию покрытия.
7. **Не объявлять старый тест новым подтверждением.** Сентябрь v1 уже использовался.
   Следующий прогон на нём будет исследовательским. Для подтверждения нужны более поздний
   терминальный период или независимые данные с сопоставимой целью. Складской набор
   проверит переносимость метода, но не качество на данном терминале или Каспии.

## Архитектура эксперимента и включение в backend

```text
Исходный журнал + правила очистки + история доступности
    → разделение по случаям/времени и аудит границы наблюдений
    → генератор одинаковых моментов прогноза
    → baseline | признаки истории → CatBoost | последовательность → LSTM
    → отдельная калибровка → единая оценка по случаям и стадиям
    → версия артефакта и карточка данных/модели
    → backend adapter → P10/P50/P90 + фактический method
```

Существующий endpoint получает пять признаков: истории для новой модели в его контракте
пока нет. Для Track A расширенные данные может собрать backend из наблюдаемых событий,
если у него есть их история и связь с контейнером. Для Track B потребуется отдельный
контракт с `as_of` и доступными событиями либо идентификатором контейнера в хранилище.
До реализации и проверки этого потока заменять веса v1 на модель с новыми входами нельзя.
Сохранить автоматический переход к алгоритму при отсутствии модели. Frontend и действующие
API в рамках этого исследования не менялись; обучение v2 ещё не выполнялось.

Monte Carlo можно использовать совместно с обученными распределениями времени стадий;
это способ расчёта сценариев, а не конкурент обучению. Однако сейчас последовательная
симуляция добавит задачи моделирования переходов и ошибок, поэтому сначала проверяем
прямой прогноз остатка.

Если появятся реальные незавершённые случаи с известной датой последнего наблюдения,
имеет смысл сравнить [XGBoost AFT survival](https://xgboost.readthedocs.io/en/stable/tutorials/aft_survival_analysis.html).
Survival учитывает цензурированные наблюдения, но не восстанавливает отсутствующие
в выгрузке случаи. Для текущего завершённого журнала это не автоматическое исправление.
