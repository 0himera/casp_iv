Проверка выполнена 12 ноября 2026 года. Найдены работающие погодные endpoint и официальные портовые публикации. Открытого готового датасета «груз → фактические этапы → задержки → очередь → документы» в этой проверке не найдено. Backend MVP должен отличать наблюдения, прогнозы, архивные материалы и синтетику.

## Проверенные запросы

```text
https://api.open-meteo.com/v1/forecast?latitude=46.35&longitude=48.04&hourly=wind_speed_10m,wind_gusts_10m,precipitation,visibility&forecast_days=1&timezone=UTC
https://marine-api.open-meteo.com/v1/marine?latitude=43&longitude=50&hourly=wave_height,wave_period&forecast_days=1&timezone=UTC
```

Необработанные ответы сохранены в `data/sources/open-meteo-weather.json` и `data/sources/open-meteo-marine.json`; сведения о запросах — `data/sources/manifest.json`. В UI fixture эти live-значения автоматически не подмешиваются: демонстрационные прогнозы должны быть воспроизводимы.

API вернул координаты модельной сетки, отличающиеся от запрошенных. Сохранять оба набора. Единицы читать из `hourly_units`, не предполагать м/с: в проверенном weather запросе ветер возвращается в км/ч. Учитывать атрибуцию Open-Meteo и поставщика модели; условия выбранного доступа проверить перед публичным коммерческим использованием.

## Что запросить у организаторов

Готовый текст для отправки самостоятельно:

> Для прототипа прогноза мультимодальных задержек нужны обезличенные данные за несколько месяцев: ID отправки, маршрут и тип груза, плановые и фактические прибытие/убытие по этапам, время входа и выхода из очереди терминала, начало/окончание обработки, подача/готовность документов и причины задержек. Нужны расписания судов с cutoff приёма груза, доступная вместимость, ограничения по погоде и совместимости груза. Просим указать часовые пояса, единицы, время появления данных в системе, разрешённое использование и возможность показать обезличенные примеры на защите. Есть ли sandbox/API для pre-clearance и тестовые статусы?

Не предполагается автоматическая отправка этого сообщения.

## Первичный контракт данных

`shipment_id, event_type, planned_at, actual_at, recorded_at, location_id, source_id, reason_code` — события этапов. `recorded_at` нужен для обучения без утечки будущих сведений. Все timestamp UTC, оригинальный timezone сохранить отдельно.

`sailing_id, departure_port, arrival_port, cargo_cutoff, departure_at, arrival_at, capacity, capacity_unit, observed_at, source_id` — расписания; неизвестная ёмкость — null, не 0.

`location, variable, value, unit, valid_at, issued_at, fetched_at, source_id` — погода. Для PDF дополнительно URL, SHA-256 файла, дата публикации и ручная/автоматическая проверка извлечения.

## Решение для хакатона

Подключать реальную погоду, использовать проверенные портовые сведения как датированные ограничения, расписание/очередь/фактическое движение — только предоставленные организаторами данные либо явная синтетика. Никакие числа текущей загрузки, доступность мест и регулярность демонстрационных рейсов не заявлять как подтверждённые.
