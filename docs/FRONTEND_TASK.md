# Задание Next.js разработчику

Собрать frontend Caspian Flow для хакатона Smart Caspian Transit. Пользователь — логист: видит риск пропустить судно, сравнивает альтернативы и собирает согласования новой версии перевозки. Интерфейс на русском, desktop first, рабочий минимум 1280 px, адаптация до 768 px.

Ты отвечаешь за Next.js-приложение и взаимодействие с REST API. Прогноз, маршрутные расчёты, авторизация действий и Casper находятся на backend. Дизайн, библиотеку компонентов и state management выбирай самостоятельно. Карта 2D, без 3D. Блокчейн показываем в паспорте и истории; криптокошелёк в P0 не нужен.

## Начать сразу

Нужны Node.js 20+, файлы `api/*` и `tools/mock-api.mjs` из этого пакета.

```bash
node tools/mock-api.mjs
```

В `.env.local` frontend:

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:4010/api/v1
```

Скопируй `api/types.ts` и готовый `api/client.ts` в общий модуль или генерируй типы из `api/openapi.json`. Схема доступна также на `http://localhost:4010/openapi.json`. Все экраны используют один adapter. Замена mock на demo-backend сохраняет DTO и меняет base URL; при внедрении настоящей авторизации дополнительно заменяется provider credentials в adapter.

Mock без npm-зависимостей; браузерный CORS разрешён для localhost:3000 и 127.0.0.1:3000. Для другого origin запускать с `FRONTEND_ORIGIN=http://localhost:3001`. Для доступа из другого компьютера каждому проще поднять собственный mock. Он намеренно слушает только localhost.

## Экраны

| URL | Содержимое | Действия |
| --- | --- | --- |
| `/shipments` | Таблица грузов: ID, направление, текущий этап, ETA, риск, статус паспорта | Открыть груз; локальные поиск и фильтр |
| `/shipments/[id]` | Карта, сводка, таймлайн, прогноз, варианты, документы, паспорт и журнал | Выбрать вариант, заменить документ, подтвердить или отклонить текущую версию |

Вторая страница может использовать вкладки. Отдельный dashboard не нужен. В mock одна отправка `shp_demo_001`, маршруты `route_astra` и `route_makh`.

Географический охват продукта: Махачкала (Дагестан), Астрахань/Оля, Актау/Курык, Энзели/Амирабад/Ноушехр, Баку/Алят, Туркменбаши. `data/ports.json` содержит проверенные координаты восьми узлов и отдельные записи без подтверждённых координат. Такие записи не ставить на карту в точку соседнего порта. Все порты можно показывать как справочный слой; selectable routes пока только из API. Наличие порта и погодных данных не означает наличие рейса между любыми двумя узлами.

На карточке:

1. Шапка: ID, тип и масса груза, направление, текущая точка, время снимка, режим данных.
2. ETA: P50 и интервал P10–P90; вероятность пропустить текущий рейс; cutoff; причины риска. `null` выводить как «Нет данных».
3. Карта: текущий и альтернативный маршрут, порты, текущая позиция. Геометрия schematic; подпись «Схема маршрута». GeoJSON coordinates всегда `[longitude, latitude]`.
4. Сравнение: ETA, риск, стоимость в рублях, CO₂e в кг, выполнимость, статус доступности и необходимость повторного согласования. Дельты сравнивать с текущим вариантом; неизвестное не превращать в ноль.
5. Документы: имя, тип, версия, SHA-256, кнопка замены. В P0 загружать файл до 1 MiB как base64 без `data:` prefix; backend вычисляет hash. Не отправлять настоящие документы в demo.
6. Паспорт: версия, hashes, готовность, роли и подтверждения, срок действия. Старые подтверждения видны в истории с `invalidated`, новые — pending/approved/rejected.
7. Журнал событий: что, когда, какой участник, версия. Транзакция кликабельна только при непустом explorer_url.

Три разных сущности нельзя смешивать: движение груза (`movement_status`), готовность паспорта (`status`) и исполнение операции (`Operation.status`). Груз может ехать при незавершённых документах.

## API

Все пути ниже относительны к `/api/v1`. JSON без общей обёртки, кроме списка `{items}`. Ошибки: `{error:{code,message}}`. Все поля и enum определены в `openapi.json` и `types.ts`.

| Метод и путь | Ответ | Назначение |
| --- | --- | --- |
| `GET /health` | Health | Проверить mock/режим |
| `GET /shipments` | ShipmentList | Список, в P0 без server pagination |
| `GET /shipments/{id}` | Shipment | Полный согласованный снимок карточки |
| `GET /operations/{id}` | Operation | Polling результата mutation |
| `POST /shipments/{id}/route-selection` | 202 Operation | Выбрать маршрут |
| `POST /shipments/{id}/document-revisions` | 202 Operation | Заменить документ |
| `POST /shipments/{id}/attestations` | 202 Operation | Подтвердить/отклонить версию от текущей роли |
| `POST /demo/scenarios` | Shipment | Переключить сценарий mock, только демопанель |

Каждый POST требует `Idempotency-Key: crypto.randomUUID()`. При сетевом повторе одного действия сохранять тот же ключ и body. Новое действие — новый ключ. `expected_revision` брать из последнего Shipment. 409 означает refetch и повторный осмысленный выбор, а не автоматическую подстановку новой версии.

Для mock передавай `Authorization: Bearer demo-logistician` либо `demo-carrier`, `demo-customs` во всех запросах: GET использует роль для `allowed_actions`, POST требует её. Это публичные локальные демоидентификаторы, не production secrets. Переключатель ролей только в демопанели. Роль определяется сервером по bearer; поля role в mutation нет. Чтение в mock открыто (без bearer используется logistician). Production auth будет отдельной серверной сессией с доступом к грузу.

```ts
// RouteSelectionRequest
{
  route_id: "route_makh",
  forecast_id: shipment.forecast.id,
  expected_revision: shipment.revision
}
// DocumentRevisionRequest
{
  document_id: "doc_invoice",
  filename: "invoice-v2.txt",
  content_base64: "bmV3IGludm9pY2U=",
  expected_revision: shipment.revision
}
// AttestationRequest — роль берётся из bearer
{ decision: "approved", expected_revision: shipment.revision }
// ScenarioRequest — только demo-logistician
{ shipment_id: "shp_demo_001", scenario: "storm", expected_revision: shipment.revision }
```

Сценарии: `normal`, `storm`, `missing_data`. Переключение меняет прогноз; оно не меняет маршрут и не сбрасывает паспорт. Прогноз mock годен 15 минут реального времени; для обновления повторно применить сценарий. Для полного сброса перезапустить mock.

После 202 показывать ожидание, сохранить operation ID и опрашивать GET operation примерно раз в секунду. Останавливать при `confirmed`, `simulated`, `failed`; после успеха refetch груза и списка. Для mock завершение — `simulated` примерно через секунду. При 30 сек ожидания показать «Проверяем выполнение» и кнопку повторной проверки, не создавать новую операцию. Сохранить ID в sessionStorage; `Shipment.pending_operation_id` позволяет восстановиться после reload.

При `network=mock` / `status=simulated` писать «Симуляция согласования». Не рисовать fake transaction hash. `confirmed` используется только будущим backend после успешной testnet-транзакции. Failed не должен показывать toast успеха.

Числа: `miss_probability` от 0 до 1; деньги в `amount_minor` (копейки); масса в тоннах; расстояние в км; выбросы в кг CO₂e. Даты ISO 8601 UTC. Форматировать отображение с явным часовым поясом (для демо Europe/Moscow). `scenario_time` — фиксированные часы сценария, `updated_at` — реальное время изменения API; не считать демодаты временем сейчас.

## Состояния и UX

- Loading skeleton; пустой список; 404; offline/retry; фоновые обновления без исчезновения карточки.
- Warning для synthetic/stale/missing данных рядом с соответствующим показателем.
- Плохой прогноз — риск; отсутствие данных — отдельное нейтральное состояние.
- Недоступный маршрут не выбирается; причина видна. «Выбрать» не означает забронировать место.
- Перед сменой маршрута показать: «Потребуется повторное согласование документов и маршрута».
- После mutation блокировать повторное действие до результата. Разрешённые действия рассчитывает API в `allowed_actions`; backend всё равно проверяет права.
- Роли: logistician заменяет документ/маршрут и подтверждает свою часть, carrier/customs подтверждают свою часть. В testnet ключи у backend.
- Цвет дополняется текстом и иконкой; клавиатурный доступ, focus и читаемые tooltip.

## Приёмка

Пройти без редактирования кода: normal → storm → выбрать альтернативу → дождаться операции → три approvals с переключением роли → ready → заменить файл → collecting и invalidated approvals. Проверить missing_data, неверный ID, 409 от старой revision, недоступный backend и перезагрузку во время операции.

Frontend не хардкодит численные прогнозы, не рассчитывает readiness и не выдаёт unknown capacity за подтверждённое место. Все показатели приходят из API. Макет можно делать на свой вкус; важнее быстро понимать причину риска и следующее действие.

Результат: исходники Next.js, `.env.example`, команда запуска, рабочие экраны на этом mock, краткая инструкция переключения на реальный backend. Начать со сквозной карточки и выбора маршрута; декоративную полировку делать после прохождения сценария.

## Дополнение: прогноз обработки контейнера v2

Готов новый backend без обязательных изменений существующих запросов.
`predictTerminalDwell()` принимает необязательный `history` завершённых событий:
`{ activity, completed_at }`. Для v2 передавать полный известный журнал, включая
BAPLIE и VESSEL_ATB; `observed_at` — конец выгрузки. Будущие события запрещены.
`method` показывает v2, v1 или алгоритм. Без истории продолжает работать v1.
[Пример запроса, ответы и ограничения](../models/terminal-dwell/v2/README.md).
Типы обновлены в `api/public-data.types.ts`; frontend автоматически не менялся.
